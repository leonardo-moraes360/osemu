# Context Mesh Framework (reference)

This document is the **in-repo** Context Mesh reference for AI agents and humans. Projects may copy a canonical version from an upstream framework repository; when none is linked, this file is the source of truth.

## Overview: Intent → Build → Learn

1. **Intent** — Capture *what* we build, *why*, acceptance criteria, and scope in `context/intent/`. Record **decisions** (ADRs) in `context/decisions/`. Load this before coding.
2. **Build** — Implement with **Plan → Approve → Execute** (see below). Respect decisions and documented patterns.
3. **Learn** — After implementation, update outcomes on decisions, intent status, changelog, and add knowledge (`learning-*`, patterns, anti-patterns) when you discover reusable lessons.

When AI work **may edit** scripts, repo code, or files under `context/`, classify the task using [`context/agents/playbook-selector.md`](agents/playbook-selector.md) and follow **one** matched playbook (`playbook-*.md`) there; omit this when the interaction is explanatory only with no edits. Repository root [`AGENTS.md`](../AGENTS.md) reinforces the same rule.

## File type separation

| Type | Location | Purpose |
|------|----------|---------|
| **Feature** | `context/intent/feature-*.md` | Feature-level intent: what, why, acceptance criteria, links to decisions. |
| **Project intent** | `context/intent/project-intent.md` | Whole-project what, why, acceptance criteria, scope. |
| **Decision (ADR)** | `context/decisions/*.md` | Recorded choices, rationale, alternatives, outcomes (updated in Learn). |
| **Knowledge** | `context/knowledge/patterns/`, `anti-patterns/` | Reusable conventions and traps. |
| **Agent** | `context/agents/` | Agent-specific notes or prompts (optional). |
| **Evolution** | `context/evolution/changelog.md` | What changed over time. |

Do not merge intent prose into decisions or vice versa: intent = goals; decisions = chosen approaches.

## Plan → Approve → Execute (mandatory)

Before substantive implementation:

1. **Plan** — Propose approach, scope, risks, files touched; cite relevant intent and ADRs.
2. **Approve** — Wait for explicit human approval (or project policy equivalent) unless the task is trivial and risk-free per team rules.
3. **Execute** — Implement, tests, update context.

Skipping approval for non-trivial changes is an anti-pattern unless policy says otherwise.

## When to create vs not create files

**Create:**

- New feature or materially new behavior → feature intent + decision when approach is chosen.
- New technology or stack choice → ADR (e.g. tech stack).
- Repeatable convention or mistake → pattern or anti-pattern doc.

**Do not create** duplicate or ornamental docs: one ADR per decision, one feature intent per feature. Avoid churn-only edits.

## Context structure

├── knowledge/

│   └── anti-patterns/

Repository root commonly includes `AGENTS.md` with setup and agent rules pointing into `context/`.

## Definition of Done (Build phase)

Work is not “done” until:

- Relevant intent and ADRs exist **before** or as soon as the decision is made (retro-ADR if fixed order).
- Code matches documented decisions and patterns.
- Tests or manual verification per project policy pass.
- **Context updated**: intent/decision status, outcomes, `changelog.md`.
- Acceptance criteria satisfied.

## Bidirectional links

- Feature intents link to their ADRs: `- [Decision: …](../decisions/NNN-slug.md)`.
- ADRs link back: `- [Feature: …](../intent/feature-slug.md)` and `- [Project Intent](../intent/project-intent.md)` when relevant.
- Use Markdown links with relative paths. Keep anchors accurate when renaming files.

## Status section requirements

Each intent feature file and ADR should include a **Status** block, for example:

- **Created**: date + phase (`Intent`, `Build`, `Learn`).
- **Status**: e.g. `Draft`, `Accepted`, `Implemented`, `Superseded`.

Update status when moving through phases; do not leave stale “Draft” after implementation unless intentionally deferred.
